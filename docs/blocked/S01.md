# [결정 필요] S01 이미지 OCR 접수 (`POST /api/script-extractions`)

명세 순서상 컨트롤러에 구현이 없는 첫 API는 S01(대본 > 이미지 OCR 접수)이다. (A01~A16은 모두 컨트롤러 매핑 존재)
문서에 OCR 처리 방식이 확정돼 있지 않아 구현하지 않았다. 코드는 변경하지 않았다.

## 확인한 문서 내용
- API 명세서 S01/S02: multipart `file`(JPEG/PNG 1~10MiB), 202 응답 `jobId/status/content/failureCode/expiresAt`, 오류 413/415/429, 접수 24시간 후 작업·결과 삭제.
- DB 설계서 3.5 `script_jobs`: `source_object_key`(OCR 원본 이미지 임시 저장 위치), `result_content`, `failure_code`, `expires_at` 등.
- AI 서버 설계서: "S01·S02는 애플리케이션 서버에서 계속 제공(OCR2)"이라고만 되어 있고, OCR 엔진·호출 방식은 기술돼 있지 않다. AI 서버 API 목록에도 OCR 엔드포인트가 없다.

## 필요한 결정 사항
1. **OCR 실행 주체/엔진**: WAS 내부 라이브러리(예: Tesseract), AI 서버(교내 로컬) 신규 엔드포인트, 외부 클라우드 OCR 중 무엇인가? AI 서버 설계서는 "외부 AI 서비스로 대본 등이 나가지 않음"을 전제로 하므로 외부 OCR은 정책 충돌 소지가 있다.
2. **원본 이미지 임시 저장소**: `source_object_key`가 가리키는 곳이 S3인지(프로필 이미지처럼 현재 임시 구현체뿐), 로컬 디스크인지. 24시간 후 이미지/작업 삭제 스케줄러 범위.
3. **비동기 처리 방식**: QUEUED→PROCESSING→COMPLETED/FAILED 전이를 WAS 내 비동기 워커로 처리할지, AI 서버 콜백/폴링으로 할지. `failureCode` 값 목록(명세에 없음).
4. **요청 제한 값**: S01의 429 기준(횟수/윈도우)이 명세에 없다.
5. **스키마**: `script_jobs` 테이블 DDL이 `docs/sql`에 없다(운영 DB 적용 필요).
6. 이미지 내용 검증(확장자 vs 시그니처) 수준.

## 선택지와 추천안
- A안(추천): AI 서버에 OCR 엔드포인트를 추가하고, WAS는 작업 접수 + 폴링으로 결과 저장. 이미지는 presigned URL 방식(S3, 기존 IF2와 동일 패턴)으로 전달. 데이터가 외부로 나가지 않는다.
- B안: WAS 내부에서 Tesseract 등으로 직접 처리, 이미지는 메모리/로컬 임시 저장. 구현은 단순하나 한글 대본 인식 품질·서버 부하 검토 필요.
- C안: 외부 클라우드 OCR. 설계서의 외부 전송 금지 전제와 충돌하여 비추천.
- 공통 제안: 429는 기존 `LoginRateLimiter` 패턴으로 설정값(`auth` 외 별도 prefix)으로 두고, 값은 팀에서 결정.
